{/* SECTION 1 - GOAL */}

<SessionSection id="goal" label="Goal">

## Understand how the model turns tokens into numbers it can reason over

Tokens are just integers -- the model cannot compare or cluster them as-is. This session shows how embeddings solve that problem by mapping every token to a point in space where similar meanings end up close together.

</SessionSection>

## Embeddings sit at the entry point of every model and retrieval system

Before attention, before generation, before any tool call -- the model converts your input tokens into vectors. That same process powers semantic search, RAG retrieval, and recommendation systems outside the model too.

## Words become points in space

The embedding layer is a lookup table. Each token ID maps to a fixed list of numbers -- called a vector. These numbers are learned during training so that tokens used in similar contexts end up at nearby points. You do not design them -- they emerge from predicting billions of next tokens.

### Similarity is distance

Once words are vectors, "how similar are these two things?" becomes a calculation -- cosine similarity or dot product. Two sentences are similar if their vectors point in roughly the same direction. This is what powers search, RAG retrieval, and duplicate detection.

### Embeddings live inside models and outside them

Inside the model, every transformer layer works entirely in vector space -- it never sees raw text again after the embedding layer. Outside the model, you can call an embeddings API to get a vector for any string and store it in a vector database for retrieval.

<SessionSection id="practical-example" label="Practical Example">

## How a support ticket router uses embeddings to replace keyword rules

A SaaS company receives thousands of support tickets daily. Their old keyword-matching system breaks whenever customers phrase things differently -- "can't log in" misses "access denied" and "locked out". They replace it with an embeddings router: embed every ticket, embed every issue category label, then route each new ticket to the nearest category by cosine similarity. New categories are added by writing a description and embedding it -- no retraining, no new rules.
