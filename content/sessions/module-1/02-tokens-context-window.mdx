## Understand the raw material an LLM actually reads -- and its hard limits

Every LLM API call you make is secretly a tokenization problem. This session shows you exactly how your text gets split into tokens, why that changes how you write prompts, and what the context window limit means for your architecture.

</SessionSection>

<SessionSection id="big-picture" label="Big Picture">

## Tokens are the unit of everything -- cost, speed, and limits

Before the model runs attention or predicts anything, your text is converted to a sequence of token IDs. That sequence is all the model ever sees -- not words, not characters, not sentences. The context window is the maximum number of those tokens the model can hold at once.

## Tokenization is not splitting by spaces

Tokenizers use Byte-Pair Encoding (BPE) -- a compression algorithm that learns common subword patterns from training data. Common words become single tokens; rare words get split into pieces. This means "unhappiness" might be 3 tokens while "the" is always 1.

### The context window is the model's working memory

The context window is the total number of tokens the model can see at once -- your system prompt, conversation history, retrieved documents, and the current message all count toward it. When you exceed the limit, either the API errors or old content gets truncated.

### When the context fills up, Claude Code compresses it with `/compact`

In AI Agents (ex: Claude Code / Cursor), your terminal conversation is also a context window. Every file you read, every command output, every back-and-forth with the agent accumulates tokens. When the window approaches its limit, Claude Code offers a `/compact` command — it summarizes the entire conversation history into a condensed handoff block, then continues from that summary instead of the raw transcript. You keep full working continuity; the token count resets to a fraction of what it was.

<SessionSection id="practical-example" label="Practical Example">

## Why Cursor can't just paste your whole codebase into the prompt

A developer opens Cursor on a mid-sized production codebase — 400 files, roughly 1,800 functions. The naive approach would be to dump the entire codebase into the context window before every question. The problem: the code files in a mid-sized company add up to at least 750,000 tokens — far beyond any single context window. Even if a model supported it, sending 750,000 tokens on every question would be slow and expensive. Cursor solves this with the same pattern you'll learn in the RAG session: index the codebase as semantic chunks, then retrieve only the relevant ones per query. **Retrieval keeps each question small, but chat history and tool output still accumulate** in the same thread. When usage gets too high, the product can **run compact automatically** (or you can trigger `/compact`) so the long transcript collapses into a short summary handoff. One simulation below walks through retrieval, then the same auth-debugging thread growing, then automatic compact.
