<SessionSection id="goal" label="Goal">

## Understand what tools are, why agents need them, and how the tool-use loop works end to end

The LLM is the brain -- it reasons, plans, and decides. But a brain with no hands can only talk. Tools are the hands: they let the agent take real actions in the world -- read a live price, write to a database, send an email, run code. This session explains what tools are, what forms they take, and exactly how the agent uses them.

</SessionSection>


{/* SECTION 2 - BIG PICTURE */}
<SessionSection id="big-picture" label="Big Picture">

## The LLM is the brain -- tools are the hands

Without tools, an LLM can only generate text based on what it knows from training and what you put in the context window. With tools, it can reach outside itself -- query real-time data, trigger real-world actions, and interact with systems. The agent decides which tool to use and when. Your application actually runs the tool. The result comes back to the agent to form the final answer.

## A tool is any callable function you expose to the model

A tool is not a special technology -- it is any function in your codebase that you describe to the model and allow it to call. That function can wrap anything: a REST API call, a database query, a Python function, a shell command, or an internal microservice. What makes it a tool is the description you attach to it -- a plain English explanation of what it does, when to use it, and what arguments it needs. The model reads that description to decide whether and how to use it.

### The model never executes tools -- it requests them, you run them

This is the most important thing to understand: the LLM does not call your API, access your database, or run your code. It reads the tool descriptions, decides which tool to use, and returns a structured JSON object with the tool name and arguments. Your application reads that JSON, executes the actual function, and sends the result back to the model. The model then uses that result to form its final answer.

### The description is what the model uses to decide when to call a tool

A tool definition has three parts: name (what your code calls), description (what the model reads to decide when and how to use it), and input_schema (the arguments the model must provide). The description is the most critical part. A vague description produces wrong or missed tool calls. A precise description tells the model exactly when to reach for this tool and what to expect back.

<SessionSection id="practical-example" label="Practical Example">

## A travel assistant that uses three tools to answer one question

A user asks: "Can I afford to fly from Cairo to London next weekend, and what is the weather like?" This requires three tools: get_flight_prices (hits a flight search API for available routes and prices), get_exchange_rate (converts GBP to EGP so the user sees local currency), and get_weather_forecast (returns London weather for next weekend). All three are independent -- the model requests all three in one response, your application runs them in parallel, and the results come back together. The model then generates one coherent answer: "The cheapest flight is £320 (approximately 16,000 EGP). London next weekend will be 12°C and rainy."
