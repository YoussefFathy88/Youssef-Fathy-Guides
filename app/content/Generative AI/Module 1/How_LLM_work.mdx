## Two distinct phases: training and inference

Every LLM goes through two completely separate phases. Training happens once and is enormously expensive — it produces the model weights. Inference happens every time you send a prompt — it is fast and uses those frozen weights to generate a response. As a developer, you only ever interact with the inference phase.

## Training: compressing the internet into weights

During training, the model reads enormous amounts of text and learns one task: predict the next token. It does this billions of times, adjusting its internal weights each time it gets a prediction wrong. By the end, those weights have compressed a statistical representation of language — and a surprising amount of world knowledge — into a single file.

### Inference: one token at a time, every time

When you send a prompt, the model runs a forward pass through all its layers and produces a probability score for every token in its vocabulary. It does not produce a sentence — it produces a distribution over what word should come next. One token is sampled from that distribution, appended to the context, and the whole process repeats until the response is complete.

### The output is a probability distribution, not a lookup

This is the most important thing to internalize. The model does not retrieve answers from a database. For every token position, it produces a ranked probability distribution across ~100,000 possible next tokens. The token actually emitted depends on that distribution and on the sampling strategy — which is why the same prompt can yield different outputs.

<SessionSection id="practical-example" label="Practical Example">

## Why your API responses are non-deterministic by default

You are building a code review tool. You send the same prompt twice and get different suggestions each time. This is not a bug — it is temperature in action. The model's distribution for code tokens is not perfectly peaked; there are several plausible next tokens at each step. With temperature at 1.0, the model samples from that spread. Set temperature to 0 and the output becomes deterministic — always the highest-probability token — which is exactly what you want for a code review tool but not for a brainstorming assistant.

<ParameterSlider
  label="Temperature"
  min={0}
  max={2}
  step={0.1}
  defaultValue={1.0}
  outputFn={(v) => {
    if (v === 0) return "Fully deterministic — identical output every run. Best for factual retrieval, code generation, and structured outputs."
    if (v < 0.4) return "Near-deterministic — very consistent with minor variation. Good for code review, classification, data extraction."
    if (v < 0.9) return "Balanced — coherent and slightly varied. Default for most chat and assistant use cases."
    if (v < 1.4) return "Creative — noticeably different each run. Good for drafting, brainstorming, and content generation."
    return "Chaotic — high variance, low coherence. Useful for creative exploration but rarely for production."
  }}
  outputExamples={(v) => {
    if (v < 0.3) return [
      "Bug found on line 12: index out of bounds.",
      "Bug found on line 12: index out of bounds.",
      "Bug found on line 12: index out of bounds.",
    ]
    if (v < 1.0) return [
      "Bug found on line 12: index out of bounds.",
      "Potential issue on line 12: array access may exceed bounds.",
      "Line 12 may throw if the array is shorter than expected.",
    ]
    return [
      "Line 12 feels adventurous — perhaps too adventurous for the array.",
      "The array on line 12 is living dangerously.",
      "I'd have a word with whoever wrote line 12.",
    ]
  }}
